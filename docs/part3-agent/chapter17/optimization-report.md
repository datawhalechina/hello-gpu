# 向量加法 Agent 实验报告

本文是 [第 17 章](./index.md) 的报告模板。当前版本在 Radeon RX 9070 XT + ROCm 7.13 + 原生 Ubuntu 24.04 上的完整 Agent 实验仍为 **🚧 待补实验**，因此这里不提供示例性能数字。填写时使用本次运行的实际文件，不引用其他设备的旧结果补空。

## 1. 任务与环境

先确定报告讨论的是哪一次实验。模型配置会影响搜索路径，硬件与计时配置会影响性能结果，两者都应记录。

| 项目 | 填写内容 |
| --- | --- |
| 任务 | `vector_add`；实际 shape、dtype、布局和容差见本次 `task.json` |
| 起点 | 本次工作区的 `baseline.py` |
| 终点 | 本次工作区的 `best.py`，同时说明是否有候选被接受 |
| 设备与系统 | 🚧 待补：实际 GPU、架构、原生系统与内核 |
| 软件环境 | 🚧 待补：ROCm、PyTorch、Triton 及环境锁 |
| 模型 | 🚧 待补：服务商、模型标识和相关生成配置；不写密钥 |
| 时间与入口 | 🚧 待补：执行日期、实际命令与工作区路径 |
| 正确性与计时 | 🚧 待补：实际种子、容差、预热、样本数、重复次数 |

## 2. 实验是否完成

读取 `agent-status.json` 后，说明状态、是否有警告、是否存在待裁决候选，再核对 `trajectory.jsonl` 是否存在有效记录。退出码 0 和一段最终回复不能单独证明实验完成。

**填写结果**：🚧 待补实验。

如果实验未完成，报告在这里说明阻塞原因和已经保留的产物即可；后续性能表保持待补。若所有候选均被拒绝，可以如实写“未找到满足接受规则的候选”，这与实验中断不同。

## 3. 哪些尝试影响了结果

挑选能解释搜索方向的少量尝试，同时包含负结果。每项分别记录：

| 信息 | 证据要求 |
| --- | --- |
| 候选改动 | 对应候选源码；不能只有模型描述 |
| 正确性 | 评测输出及任务条件 |
| 候选延迟 | 原始计时样本与统计口径 |
| 配对裁决 | 当时比较的当前版本、配对改进和接受原因 |
| 下一步 | 说明观察怎样影响后续假设 |

**当前记录**：🚧 待补实验。`trajectory.jsonl` 只是裁决摘要，不会自动包含每次编译尝试、所有源码、完整工具调用和原始采样。缺失证据应直接说明，不从旧图还原成伪造的原始日志。

## 6. 结论与限制

结论先回答有没有找到值得保留的版本，再解释变化发生在哪里。将“源码可确认的变化”“工具实测结果”“模型估算”和“尚待验证的原因”分别写清。

**当前结论**：🚧 待补实验。尚不能报告本版本在主线环境上的加速倍数、有效方向或接受次数。

即使后续实验获得收益，也只覆盖本次任务、输入和设备。若没有人工优化对照、更多 shape 或端到端模型测试，不扩展为这些范围的结论。
