# 第 2 篇：经典算子与 Kernel 实战

假设我们已经能测准一段 GPU 程序的时间，也能从 trace 里找到最慢的 kernel。接下来怎样改它？从这一篇开始，我们拿六种具体算子做实验：先写出一个容易理解的正确实现，测出它的表现，再带着具体问题修改和比较。

六章会逐步增加问题的难度。数组加法的每个输出彼此独立；求和需要让线程合作；矩阵乘还要让多个输出复用输入。学会这些基本模式后，我们再把它们组合成 Attention 和 RMSNorm。

## 怎样阅读这一篇

每章先用一个能手算的小输入解释算法，配有可播放、可单步查看的动画。画面默认静止，先看清当前步骤再前进即可；动画里的时间只用来展示计算关系，不表示真实 GPU 耗时。

理解算法后，在 **HIP / Triton 标签页**中选择一条实现路线。第一次阅读只学一种语言也可以，页面会在本次浏览中记住选择。两条路线共用数学问题，各自从初版出发做实验；想比较不同的分工方式时，再切换标签。

如果还不熟悉 thread、block、program 或 tile，可以先读[附录 D：HIP 与 Triton 的编程范式](../appendix/programming-models/index.md)。附录用同一个数组加法解释两种写法，第 8 章也会在需要时给出入口。

## 一轮优化怎样进行

我们把每条路线最先保留的正确实现称为**基线（baseline）**。它是后续比较的起点，应该自然、清楚，并覆盖本章约定的输入范围。之后每轮按六步推进：

1. **建立基线。** 先算清一个小例子，检查初版的输出，并记录时间。
2. **观察表现。** 结合计时、trace 和数据流图，找出一个值得研究的问题。例如，同一份输入是否被反复读取，某个阶段是否产生了很多中间结果。
3. **提出假设。** 说明下一项改动为什么值得试。例如，让一组计算多处理一些数据，能否减少中间结果和后续合并的工作。
4. **实施改动。** 一轮集中修改一个设计选择，并写清它连带改变了什么。增大数据块可能减少工作组数量，也可能增加每组要保留的数据。
5. **校验与复测。** 先检查答案和边界输入，再用相同输入规模、数据类型与计时范围重复测量。
6. **比较与决策。** 看新版本是否改善了当前问题，再决定保留、回退，还是继续验证另一个假设。变慢或没有稳定差异，也要留下记录。

读结果图时，同时找三个位置：**最初基线、本轮修改前的版本、本轮新版本**。第一轮的前两者可以是同一个版本。这样既能看见这一轮的变化，也不会丢掉从起点走了多远。只有输入规模和计时范围一致的时间才放在一起比较；多阶段算法的完整路径也要包含最终合并。

图中的柱或点说明时间，旁边的范围说明多次运行的波动。若标注为“三个进程各自中位数的最小—最大值”，它就不是置信区间。差异与波动接近时，可以先保留“尚未观察到稳定改善”的判断，再增加测量。

## 三种对照各回答什么

正确性和性能需要不同的参照。后文遇到参考实现或 baseline 时，可以先确认它负责回答哪一个问题：

| 对照 | 回答的问题 | 例子 |
| --- | --- | --- |
| 正确性参考 | 结果是否符合公式和误差要求？ | 手算、CPU 参考或 PyTorch 表达式 |
| 路线基线 | 这条路线的修改带来了什么变化？ | HIP 的初版、Triton 的初版 |
| 库性能参照 | 自己的实现与现成库在这个问题上相差多少？ | 相同语义和计时范围下的 PyTorch 算子 |

同一个库函数可以参与校验和计时，但这两个用途要分别看待。通过正确性检查之后，才能讨论速度；比某个教学初版快，也不等于已经超过库实现。

## HIP 与 Triton 分别改什么

两条路线使用同样的实验方法，直接控制的对象有所不同：

| 设计选择 | HIP 路线 | Triton 路线 |
| --- | --- | --- |
| 一份工作处理多少数据 | 线程下标、block 大小、每线程的循环 | program 负责的数据块、块形状与 program 数量 |
| 怎样合作与保留中间值 | 局部累加、LDS、shuffle 与屏障 | 张量运算、归约轴、`num_warps` 与分阶段边界 |

例如，Triton 的 `BLOCK_SIZE` 表示一个 program 处理的逻辑元素数，不能直接当作 HIP 的线程数。具体元素怎样分配给执行线程，还需要编译器安排。两条路线各自选择合适的初版和改动，不必拥有相同数量的版本。

## 从实现走到实验

每章的源码在 `code/part2-kernels/chapterN/`。HIP 和 Triton 实现、运行入口、实验记录放在一起；正文摘录关键片段，完整输入生成、校验和计时仍以源文件为准。

| 入口 | 用途 |
| --- | --- |
| `run_all.sh` | 运行本章实现与正确性检查 |
| `profile_all.sh` | 按实现分别采集 trace；参数以各章说明为准 |
| `run_rounds.py` | 按本章的对照矩阵重复测量，保存各进程的样本与配置 |
| `verify_rounds.py` | 在独立进程与新目录中确认候选结果 |
| `plot_rounds.py` | 读取本章发布数据，重画逐轮比较图 |
| `EXPERIMENT.md` | 记录环境、命令、源码身份和结果边界 |
| `evidence/rounds/` | 保存本轮图表所依据的环境、配置和统计 |

本书当前环境统一为 **Radeon RX 9070 XT（gfx1201）+ ROCm 10.0 + 原生 Ubuntu 24.04**。已有性能表保留采集时的 ROCm 版本；每组数字只描述相应输入、源码和测量协议。

做完一次练习，留下输入、参考答案、测量范围和观察就已经很有价值。某个版本变慢同样值得记录：它提醒我们，减少一次写回、增加一个 tile 或少启动一个 kernel，都需要放回完整程序中验证。
